# 소상공인을 위한 Agentic SaaS 구축 1시간 실습 — 강사 대본

총 15장 · 60분 · Gate 2 승인 리서치 기준

## 슬라이드 1: 오프라인 검증된 예약 SaaS 만들기

- **시간**: 2분
- **목적**: 결과의 범위를 오프라인 검증 코드베이스로 정확히 약속한다.
- **화면 단서**: 완성된 `한 자리, 두 손님, 네 경계` 사례를 가리킨다.

60분 뒤 남는 것은 오프라인 검증을 통과한 예약 SaaS 코드베이스입니다. 한 자리,
두 손님, 네 경계를 따라 상태와 책임이 있는 제품을 생성하는 과정을 봅니다. setup,
인증된 live QA, 배포는 그다음 단계입니다. [C1][R1-R4]

## 슬라이드 2: 장재현, 만들고 운영하며 가르칩니다

- **시간**: 2분
- **목적**: 개인정보·학력 없이 강의와 직접 관련된 제작 경험만 제시한다.
- **화면 단서**: 100+, 200+, 10Y를 차례로 짚는다.

저는 생성형 AI SaaS를 백 개 넘게 만들었고, 사이드 프로젝트는 이백 개 이상,
AI 기반 풀스택 개발은 10년째 하고 있습니다. 오늘은 이력보다 여러분이 다시 실행할
수 있는 경로에 집중합니다.

## 슬라이드 3: 적용 업종을 고릅니다. 동률이면 헤어살롱

- **시간**: 3분
- **목적**: 네 업종 중 하나를 고르고 capability 밖 요구를 분리한다.
- **화면 단서**: 거수, 동률이면 헤어살롱.

네 업종 중 하나를 고르겠습니다. 손을 들어 주세요. 동률이거나 무응답이면
헤어살롱을 사용합니다. 오늘은 capability matrix 안에서만 만들고, 새 기능 요청은
후속 확장 목록으로 분리합니다. [C4][R15-R16]

## 슬라이드 4: 예약 화면 뒤에는 운영 시스템이 있다

- **시간**: 4분
- **목적**: Agentic SaaS를 상태와 책임으로 정의한다.
- **화면 단서**: 비어 있는 `최종 책임자`를 청중에게 묻는다.

예약에는 충돌, 시간, 소유권, 사람에게 넘기는 시점이라는 네 경계가 있습니다.
빈칸의 답은 서버 mutation입니다. Convex는 트랜잭션 기반을 제공하고, Jeomwon
mutation이 예약 정책을 구현합니다. [C3][R11-R14]

## 슬라이드 5: Jeomwon은 생성기와 생성된 앱으로 나뉩니다

- **시간**: 4분
- **목적**: coding-time plane과 runtime plane을 분리한다.
- **화면 단서**: 왼쪽 생성기에서 오른쪽 런타임으로 한 번만 이동한다.

왼쪽은 만드는 시간이고, 오른쪽은 실행 시간입니다. 만드는 쪽은 정해진 템플릿을
복사하고 닫힌 domain pack을 주입한 뒤 오프라인 검증합니다. 실행 쪽에서는 두
Next.js 앱과 Convex backend가 독립적으로 돌아갑니다. [C1][C2][R1-R10]

## 슬라이드 6: Next.js·Convex·Vercel은 무엇을 맡나

- **시간**: 4분
- **목적**: 화면·데이터 규칙·배포의 소유권을 구분한다.
- **화면 단서**: 세 열을 읽은 뒤 독립 rollout 문장을 강조한다.

Next.js는 화면, Convex는 데이터와 서버 규칙, Vercel은 두 Next.js 앱을
배포합니다. Web과 App은 독립 프로젝트이고 Convex는 별도 deployment입니다.
세 단위의 롤아웃은 원자적이지 않으며 환경 변수와 배포 키도 각각 확인합니다.
[C2][R6-R10]

## 슬라이드 7: Convex DB, 데이터와 서버 규칙을 한곳에

- **시간**: 5분
- **목적**: Convex의 네 실행 요소를 비개발자 언어로 설명한다.
- **화면 단서**: Tables → Queries → Mutations → Scheduler 순서로 읽는다.

Tables는 현재 상태를 저장합니다. Queries는 구독 중인 화면에 최신 결과를 보냅니다.
Mutations는 읽기와 쓰기를 한 트랜잭션으로 처리합니다. Scheduler는 나중에 실행할
일을 등록하지만 정확한 시각은 보장하지 않습니다. [C3][R11-R13]

## 슬라이드 8: 프롬프트보다 강한 것, mutation 불변식

- **시간**: 4분
- **목적**: 충돌·홀드·취소·소유권이 mutation의 책임임을 확인한다.
- **화면 단서**: held 취소와 confirmed/rescheduled 취소의 갈림길을 비교한다.

최종 보장은 mutation이 담당합니다. held 예약을 유효하게 취소하면 cancelled로
바뀌고 수용량을 돌려줍니다. confirmed 또는 rescheduled 예약을 취소창 안에서
취소하면 escalated로 바뀌고 수용량을 유지합니다. threadId는 라우팅 문맥이며
신원이나 권한이 아닙니다. [C3][R14]

## 슬라이드 9: 대화가 닫힌 설정이 되고 미리 구현된 앱을 바꿉니다

- **시간**: 5분
- **목적**: 인터뷰에서 닫힌 설정, 생성 코드로 이어지는 경로를 보여준다.
- **화면 단서**: 네 단계에서 임의 코드 생성이 없음을 강조한다.

운영 언어로 인터뷰한 답을 services, resources, calendar, policies, copy 필드로
채웁니다. inject는 정해진 설정 위치만 쓰고 verify가 결과를 검사합니다. 핵심은 긴
프롬프트가 아니라 운영 규칙을 필드로 확정하는 일입니다. [C1][R1-R4]

## 슬라이드 10: 수업 후 그대로 쓰는 프롬프트 사다리

- **시간**: 4분
- **목적**: 인터뷰·구조화·검토 프롬프트와 변형 과제를 회수한다.
- **화면 단서**: 왼쪽 프롬프트를 읽고 오른쪽 빈 풋살장 사례는 채우지 않는다.

수업 후에는 이 프롬프트 하나를 업종 인터뷰와 설정 검토에 사용합니다. 오른쪽은
풋살장 사례이고 빈칸은 자신의 업종에 맞게 채웁니다. [C6][C7][R21-R25]

## 슬라이드 11: 라이브, scaffold → inject → verify

- **시간**: 10분
- **목적**: 선택 업종 코드베이스 생성과 오프라인 계약 통과를 관찰한다.
- **화면 단서**: 명령 실행 전 target·name·pack을 소리 내어 확인한다.

scaffold는 정본 template을 새 폴더로 복사합니다. inject는 닫힌 설정을 쓰고
verify는 install, typecheck, lint, build를 검사합니다. 성공 문구는 OFFLINE
VERIFIED입니다. 대화 입력은 “2시간 뒤”, “내일”처럼 지원하는 표현을 쓰거나 UI에서
슬롯을 직접 고릅니다. [C1][C4][R1-R4][R16]

## 슬라이드 12: 참조 UI로 제품 동선을 봅니다

- **시간**: 5분
- **목적**: 고객·채팅·운영자·위젯 동선을 provenance와 함께 보여준다.
- **화면 단서**: `REFERENCE UI` 라벨을 먼저 읽는다.

이 화면은 bootstrap 결과와 분리된 사전 준비 참조 UI입니다. 고객은 예약이나
채팅으로 들어오고, 운영자는 대시보드와 에스컬레이션을 봅니다. 캘린더나 좌석
위젯은 domain pack 설정에 따라 달라집니다. [C2][C4][R6-R10][R15-R16]

## 슬라이드 13: 생성 성공과 운영 성공은 같은 체크가 아닙니다

- **시간**: 3분
- **목적**: 생성 이후 운영 준비를 별도의 네 단계로 분리한다.
- **화면 단서**: `OFFLINE VERIFIED`에서 하드 스톱한다.

후속 단계는 Convex login, setup, QA, 배포입니다. bun setup에서 계정, OAuth,
Convex dev deployment, 환경 변수를 연결합니다. 그 뒤 bun run qa가 dev Convex
데이터를 초기화하고 mock runtime에서 11개 계약 게이트를 실행합니다. 실제 Google
운영자 CRUD는 별도 smoke 테스트입니다. 오늘은 이 단계를 실행하지 않았고
bootstrap과 VERIFY PASS, QA SKIP 상태만 확인했습니다. [C1][C2][R3-R4][R8-R10]

## 슬라이드 14: 결제 옵션 ≠ 예약 결제

- **시간**: 3분
- **목적**: Polar 계정 구독과 예약 건별 결제를 분리한다.
- **화면 단서**: 가운데 `NO LINK`의 빈 공간을 유지한다.

계정 플랜 구독과 예약 결제는 연결되어 있지 않습니다. 기본 꺼짐 상태의 계정
구독에는 checkout, portal, webhook 경로가 있습니다. 예약 lifecycle에는 건별
checkout, 금액, 통화, 주문, 보증금, 환불 상태 연결이 없습니다. reservation hold는
슬롯 임시 점유이지 카드 승인 hold가 아닙니다. Polar sandbox E2E는 이번 조사에서
실행하지 않았습니다. [C5][R17-R20]

## 슬라이드 15: 48시간에서 72시간 뒤, 새 업종으로 다시 실행

- **시간**: 2분
- **목적**: 자료·첫 프롬프트·첫 명령을 회수하고 지연 재현을 약속한다.
- **화면 단서**: 빈 재구성 칸은 끝까지 채우지 않는다.

월요일에 일곱 단계를 다시 밟으세요. 오늘과 다른 업종을 고르고, 빈칸에서 한 자리,
두 손님, 네 경계를 다시 정의합니다. 48시간에서 72시간 뒤 재현 여부는 이 과제로
확인합니다. 저장할 것은 자료 폴더, 첫 인터뷰 프롬프트, 첫 bootstrap 명령 세
가지입니다. [C6][C7][R21-R25]
